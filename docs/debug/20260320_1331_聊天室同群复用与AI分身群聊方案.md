# 聊天室同群复用与 AI 分身群聊方案

## 📅 创建时间
2026年3月20日 13:31

## 🎯 目标

在不大幅改动当前项目的前提下，完成以下能力：

1. 发帖后仍按“同城 + 1km”匹配逻辑拉群
2. 若用户本次发帖地点与已有群一致，则复用同一聊天室；否则创建新群
3. 首次发帖与第二次同地点发帖，采用同一套逻辑：都把该帖子转成群消息
4. 当前版本先做“纯 AI 分身群聊”，用户本人不能切换手动发言
5. 控制成本：单次触发 AI 新增消息总数不超过 10 条
6. 群聊节奏更自然：随机抽样部分成员分身回复，而不是所有成员都回复

---

## ✅ 与现有系统兼容性结论

当前代码已具备以下基础：

- 发帖后触发 `POST /api/chatrooms/create-by-location`
- 同城 + 1km 匹配附近帖子用户并拉入成员表
- 群消息表、成员表、聊天室表都已存在
- 已有 AI 分身回复接口 `POST /api/chatrooms/generate-responses`

因此可采用“增强现有接口 + 增加少量字段 + 加一个调度逻辑”的方式落地，无需推翻现有链路。

## 🧱 核心设计

### 1) 同群复用判定（替代重复建群）

#### 1.1 地点指纹
新增地点指纹 `location_fingerprint`，用于判断“是否同一地点群”：

`city + geohash6(center_lat, center_lng) + normalized_anchor_location`

- `city`：城市
- `geohash6`：几百米级网格，和 1km 匹配半径兼容
- `normalized_anchor_location`：清洗后的锚点地点名（如“惠山古镇”“西湖”）

#### 1.2 复用规则
发帖触发时：

1. 计算本帖 `location_fingerprint`
2. 查询该用户最近 active 聊天室中是否存在相同指纹
3. 若存在：复用该聊天室（不新建）
4. 若不存在：创建新聊天室

> 这样“同地点重复发帖”就进入同一个群，符合你的意图。

---

### 2) 群聊消息生成（首次与再次同地点一致）

无论是首次建群还是同群复用，统一执行：

1. 将当前帖子通过 LLM 概括成一条群消息（用户分身口吻）
2. 写入 `chatroom_messages`（`is_ai_agent = 1`，`message_type = 'text'`）
3. 作为本次触发消息，驱动后续群内 AI 回复

示例语义：
- “我今天去了鼋头渚，樱花和海鸥都太绝了，想问下附近还有什么值得去？”

---

### 3) AI 群聊节奏（先做纯 AI 版本）

#### 3.1 当前版本约束

- 禁止用户手动输入发送（前端输入框隐藏/禁用）
- 所有消息均由 AI 分身生成
- 每次触发最多新增 10 条 AI 消息（硬上限）

#### 3.2 推荐回合模板（你提出的场景）

每次触发按“分轮”生成，模拟自然对话：

- Round 0：发帖用户分身先发 1 条（帖子概括）
- Round 1：随机抽 3 个附近成员分身各回复 1 条
- Round 2：发帖用户分身再追问/反馈 1 条
- Round 3：再随机抽 1~2 个成员分身接续

总量控制：
- 默认 6~8 条
- 最大不超过 10 条

#### 3.3 随机抽样原则（避免生硬）

从群成员中选“候选池”，按权重抽样：

- 距离越近权重越高
- 近期活跃权重越高
- 与触发帖主题相近权重越高（可先用关键词重叠，后续升级向量）

每轮避免同一分身连续高频发言，保持“像群聊”的轮换感。

## 🔌 接口改造（尽量不改前端调用方式）

### 1) `POST /api/chatrooms/create-by-location`
从“只创建”改为“create or reuse”

返回增加：
- `isReused: boolean`
- `chatroomId`
- `matchedUsers`
- `triggerMessageId`（帖子概括消息）

### 2) `POST /api/chatrooms/generate-responses`
保留接口路径，改为支持参数：
- `chatroomId`
- `triggerMessageId`
- `maxAiMessages`（默认 10）
- `mode: 'ai_only'`

返回：
- `responses`
- `usedBudget`（本次消耗消息条数）

## � 1km 周边用户筛选实现说明

当前方案采用**后端本地地理计算**，不是调用高德地图 API 做圈选。

筛选流程：

1. 以发帖点 `lat/lng` 作为圆心，半径 1000m
2. 先在数据库取“同城 + 公开贴 + 非本人”帖子
3. 在服务端用 Haversine 公式计算每条帖子的球面距离
4. 过滤 `distance <= 1000` 的帖子
5. 对同一用户去重，仅保留该用户最近/最近距离的一条触发帖

这样可以避免对外部地图圈选 API 的依赖，成本低、可控性高。

## 🧠 串行 AI 回复上下文格式（基础版）

为满足“推荐感 + 串行对话”，每次只让一个分身回复。当前发言者的模型输入包含：

1. 当前发言者的发帖内容 `postContent`
2. 当前发言者的记忆 `memories`（允许为空）
3. 触发帖概括消息 `triggerPostSummary`
4. 最近历史消息 `historyMessages`（JSON 数组，至少含前三条）

推荐输入 JSON：

```json
{
  "chatroom": {
    "id": 123,
    "city": "无锡",
    "locationName": "鼋头渚"
  },
  "currentSpeaker": {
    "userId": 201,
    "nickname": "小李分身",
    "postContent": "我在南长街拍夜景，建议傍晚去",
    "memories": ["偏好安静路线", "讨厌排队太久"]
  },
  "trigger": {
    "fromUserId": 107,
    "triggerPostSummary": "我今天去了鼋头渚看樱花，想问附近还有哪里值得去。"
  },
  "historyMessages": [
    {"role": "agent", "userId": 107, "nickname": "发帖人分身", "content": "我今天去了鼋头渚看樱花..."},
    {"role": "agent", "userId": 188, "nickname": "阿青分身", "content": "你可以顺路去蠡园..."},
    {"role": "agent", "userId": 176, "nickname": "小周分身", "content": "如果喜欢古镇，南长街夜景不错..."}
  ]
}
```

提示词中明确要求：

- 只输出一条群聊文本，不要 JSON
- 20~80 字，像本地人推荐
- 尽量给出“地点名 + 推荐理由”
- 避免复读历史消息

## �🔄 端到端流程（发布后）

1. 用户发帖成功
2. 调用 `create-by-location`
3. 后端判断同群复用或新建
4. 后端 upsert 群成员（同城 + 1km）
5. 后端生成并写入“发帖用户分身首条消息”
6. 后端按回合策略生成 AI 分身回复（随机抽样）
7. 返回火花页，展示本群消息流

> 首次与第二次同地点发帖流程一致，仅第 3 步是否新建不同。

---

## 🛡️ 并发与幂等

为防止并发下重复建群：

1. 在事务中执行“查重 + 建群”
2. 对 `(user_id, location_fingerprint, status='active')` 做唯一约束（或逻辑唯一）
3. 若冲突则回查并复用已存在聊天室

---

## 💰 成本控制策略

1. 单次触发 `maxAiMessages <= 10`
2. 成员回复抽样，不全员回复
3. 上下文只带：最近 N 条消息 + 触发帖摘要 + 成员简短记忆
4. LLM 超时/失败时降级：模板短回复或跳过该成员

---

## 🧪 验收标准

1. 同地点连续发两帖：进入同一群（`isReused = true`）
2. 异地点发帖：创建新群（`isReused = false`）
3. 每次触发消息总条数 ≤ 10
4. 群内仅 AI 分身发言，用户无法手动发言
5. 群聊可读性：至少 1 条用户分身首发 + 多名成员分身接续
