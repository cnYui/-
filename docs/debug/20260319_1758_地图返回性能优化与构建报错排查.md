## 二、核心原因说明

### 2.1 为什么 `progress` 轮询复测不再出现 500

复测过程中，连续多次请求：

- `GET /api/travel/progress/53`

均返回 200，未出现 500，核心原因是此前已在后端完成以下修复（`backend/src/routes/travel.js`）：

1. **`dailyPlans` 清洗与兜底**：对异常结构、缺失字段、非法点位做过滤与安全回退。
2. **自动推进容错**：在 progress 自动推进时，对当前 day/step 边界与景点数据异常做保护，不再让脏数据直接抛异常。
3. **计划缺失安全返回**：当计划数据异常或为空时返回可预期状态，而不是进入未捕获错误链路。

因此，原先由“脏计划数据 + 自动推进边界”触发的 500 已被根因修复。

### 2.2 为什么 `node --check src/js/map-travel.js` 通过

- `node --check` 只做 **JavaScript 语法检查**。
- 该文件语法合法，所以检查通过。
- 它不会检查 Vite 多页面入口配置、HTML script 类型、资源是否存在等构建层问题。

### 2.3 为什么 `vite build` 仍失败（与本次地图改动无关）

根据构建输出与配置，失败原因是项目已有构建配置问题：

1. **Rollup 入口声明了不存在页面**
   - 文件：`frontend/vite.config.js`
   - 配置里有：`encounter: resolve(__dirname, 'src/pages/mobile/encounter.html')`
   - 但该入口文件缺失，导致：`Could not resolve entry module "src/pages/mobile/encounter.html"`

2. **多个 HTML 中普通 `<script>` 非 module（告警）**
   - Vite 在构建多页面时，普通 script 不会被按模块方式打包，出现提示：
   - `can't be bundled without type="module" attribute`
   - 这部分是当前项目历史写法，属于既有问题，不是本轮地图脚本新增导致。

## 三、实现内容

### 3.1 marker 分批渲染（首屏先近后远）

**文件**: `frontend/src/js/map-travel.js`

**新增策略**：

1. 对帖子按“与当前地图中心距离”排序，优先渲染近点。
2. 首批立即渲染 `FIRST_BATCH_MARKERS = 30`。
3. 其余以 `MARKER_BATCH_SIZE = 40` 分批追加，每批间隔约 `16ms`，降低主线程阻塞。
4. 增加 `markerRenderVersion` 与 `markerBatchTimer`：
   - 新一轮渲染开始时使旧批次失效
   - 拖拽/缩放触发重载时可安全中断旧批次

**效果**：
- 首屏更快出现可见点位
- 点位较多时减少“一次性 add 全量 marker”造成的卡顿

### 3.2 bfcache 友好返回策略

**文件**: `frontend/src/js/map-travel.js`

**改造点**：

1. 将 `window.onload = ...` 改为 `initMapOnce()` + `DOMContentLoaded`，并用 `mapInitialized` 防重入。
2. 监听 `pageshow`：
   - 若页面来自 bfcache 且 `map` 仍在，执行 `map.resize()`，避免重建地图实例。
   - 仅在 marker 丢失时补拉缓存/数据，避免每次返回都全量重初始化。
3. 保留原有 `pagehide`/`visibilitychange` 的视角保存，配合已有会话缓存恢复。

**效果**：
- 从帖子详情返回主页面时，优先复用缓存页面状态
- 减少地图与 marker 的重复初始化
